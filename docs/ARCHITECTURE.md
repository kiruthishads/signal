# Architecture

## System overview

```
Browser
  │
  ▼
Vercel (Next.js 16 App Router)
  │  Auth: Supabase SSR cookies (httpOnly)
  │  Data: proxy → /api/v1/* → Render
  │
  ├── /auth/callback        → exchanges PKCE code for session
  ├── /auth/syncing         → client calls POST /v1/auth/sync
  ├── /dashboard            → protected, server-rendered
  ├── /profile/[username]   → public, ISR (revalidate: 60s)
  └── /api/v1/*             → Next.js rewrite proxy to Render
           │
           ▼
        Render (FastAPI)
           │  Uses: SUPABASE_SERVICE_ROLE_KEY (bypasses RLS)
           │         ANTHROPIC_API_KEY
           │         GITHUB_TOKEN (per-user, ephemeral)
           │
           ├── POST /v1/auth/sync      → upsert users row
           ├── POST /v1/analysis/start → kick off pipeline
           ├── GET  /v1/analysis/{id}  → poll job status
           ├── GET  /v1/profiles/{u}   → public profile data
           └── GET  /health
                    │
                    ▼
                 Supabase
                 PostgreSQL + RLS
```

## Authentication flow

```
1. User clicks "Get profile" on landing page
2. LoginButton → supabase.auth.signInWithOAuth({ provider: "github", scopes: "read:user public_repo" })
3. Supabase redirects → GitHub authorization page
4. GitHub → Supabase → /auth/callback?code=<pkce_code>
5. Next.js route.ts exchanges code → session stored in httpOnly cookies
6. Redirect to /auth/syncing
7. Client calls POST /v1/auth/sync with Authorization: Bearer <jwt>
8. FastAPI validates JWT with SUPABASE_JWT_SECRET, upserts users row
9. Redirect to /dashboard
```

Security properties:
- JWT is validated server-side on every FastAPI request via `SUPABASE_JWT_SECRET`
- Middleware uses `getUser()` (network round-trip to Supabase), not `getSession()` (local cookie parse)
- GitHub token is fetched by the backend from Supabase provider_token per request — never stored long-term

## Analysis pipeline

```
POST /v1/analysis/start
  │
  ├── Create analysis_jobs row (status: pending)
  │
  ├── Background task:
  │     1. Fetch GitHub repos via REST API (read:user public_repo)
  │     2. Score each repo: commit frequency, code size, language diversity, PR patterns
  │     3. Select top N repos by composite score
  │     4. For each selected repo:
  │           a. Fetch README, recent commits, file tree
  │           b. Send to Claude Sonnet → structured TE/PC/CQ scores + evidence citations
  │           c. Anti-hallucination cap: TE ≤ objective_ceiling + 1.5 normalized points
  │     5. Aggregate scores across repos (weighted by repo significance)
  │     6. Generate recommendations via Claude Haiku
  │     7. Upsert capability_profiles, evidence_citations, recommendations
  │     8. Mark analysis_jobs status: completed
  │
GET /v1/analysis/{id} — poll every 3s from client until completed/failed
```

## Database schema

10 tables, all with RLS enabled.

| Table | Purpose |
|---|---|
| `users` | GitHub identity, OAuth tokens |
| `repositories` | Repo metadata per user |
| `artifacts` | Files/commits used as evidence |
| `analysis_jobs` | Pipeline run status and metadata |
| `capability_profiles` | TE/PC/CQ scores (one current per user) |
| `evidence_citations` | Specific artifact → score justification links |
| `role_templates` | 10 canonical job roles with required skill levels |
| `gap_analyses` | Delta between user profile and target role |
| `recommendations` | Actionable items generated by Haiku |
| `profile_views` | Public profile view counts |

RLS policy pattern:
- `service_role`: ALL operations (backend uses this — bypasses RLS for all SIGNAL data writes)
- `authenticated`: SELECT own rows (users, analysis_jobs, capability_profiles)
- `anon`: SELECT on public-facing rows only (users username/avatar, capability_profiles is_current=true, evidence_citations, role_templates)

## Scoring model

Scores are on a 1.0–9.0 scale across three dimensions:

| Dimension | Measures |
|---|---|
| **TE** Technical Execution | Code quality, architecture decisions, complexity management, testing |
| **PC** Project Complexity | Scope, sustained effort, system integration, novel problem-solving |
| **CQ** Conceptual Quality | Design thinking, documentation, API design, engineering judgment |

Anti-hallucination constraint: the AI scoring layer cannot push TE more than 1.5 normalized points above the objective ceiling derived from repository metrics (commit count, code size, language depth). This ensures scores can always be defended with citable evidence.

## Key engineering decisions

**Why Next.js App Router + Supabase SSR?**
Auth state lives in httpOnly cookies, not localStorage. Middleware validates the JWT on every request before the page renders. The alternative (client-only auth) would expose the dashboard to unauthenticated requests during hydration.

**Why proxy through Next.js rather than call Render directly from the browser?**
The backend URL is hidden from the client. CORS is avoided. The proxy rewrite in `next.config.ts` routes `/api/v1/*` to `NEXT_PUBLIC_API_URL` — changing backends requires only an env var update and Vercel redeploy.

**Why service_role for all DB writes?**
RLS row-level policies work well for reads (anon public profile, authenticated own data). For writes (creating analysis results, upserting profiles) the FastAPI backend acts as a trusted intermediary — it authenticates the user via JWT before writing, then uses service_role to write the data. This avoids complex RLS write policies while keeping the security invariant: no unauthenticated writes possible.

**Why Claude Haiku for recommendations?**
Recommendations are generated after the expensive Sonnet analysis pass. Haiku is sufficient for structured suggestion generation and cuts per-analysis cost significantly while keeping latency low.
